# 脆弱性の複数トラフィック証跡

> 本書は、上流（原典）ARTEX の設計文書を日本語に翻訳したものです。脆弱性とトラフィックの証跡を結び付ける機能の設計を、コントリビューターとメンテナーのために整理しています。原文（中国語）は [`finding-traffic-evidence-zh.md`](finding-traffic-evidence-zh.md) に保存されています。
>
> 英語版: **[Vulnerability multi-traffic evidence (finding-traffic-evidence-en.md)](finding-traffic-evidence-en.md)**.

脆弱性の詳細画面の「関連トラフィック」は、複数ページにまたがる複数選択、用途と説明の入力、並べ替え、紐付けの解除をサポートします。トラフィックページでも複数のレコードを一度に選択し、既存の脆弱性一つに紐付けることができます。作業が継承した脆弱性の証跡は読み取り専用です。変更するには元の作業に入る必要があります。

システム設定の「Agent の自動トラフィック紐付け」は既定でオフになっており、読み取り・変更のインターフェースは `/api/settings` の `agent_traffic_binding` です。この機能をオンにすると、リクエスト/レスポンスの参照、ツール呼び出し、プロンプトに起因するトークン消費が増えます。次のラウンドの Agent から新しい設定が使われます。オフのときは、自動紐付けのパラメータと補完用の紐付けツールを隠し、自動紐付けの案内を注入せず、すでに実行中のセッションが新たに送信する自動紐付けを拒否します。手動による紐付け、トラフィックの取得、保存された証跡の読み取りとエクスポートは影響を受けません。

機能をオンにした後の基本の流れは「発見事項の登録 → レポート Agent の自動トリガー → トラフィックの照合・紐付け → 最新の証跡バージョンでレポートを作成」です。報告者は `evidence` に検証コマンド、主要な出力、すでに確保した実際のトラフィック ID と用途を残します。レポート Agent は脆弱性の詳細と実行記録を統合し、`traffic_search` / `traffic_get` で確認したうえで `bind_finding_traffic` を呼び出し、最新の `version` を読み取ってレポートを保存します。スイッチをオフにした場合、レポート Agent は元のトラフィックの検索・読み取りツールを追加で受け取らず、自動紐付けも行いません。ただし、手動で紐付けされたスナップショットを読み取ってレポートを生成することはできます。

既存の呼び出し元との互換性も保たれています。`report_finding` の `traffic_refs` / `evidence_hint_id` で、従来どおり明示的にその場で紐付けることができます。紐付けは任意です。TCP などの非 HTTP の脆弱性である場合、まだ収集していない場合、正確なレコードが見つからない場合には、参照を省略しても正常に報告でき、レポートを作成できます。コマンド出力、ログなど検証可能なその他の証跡は残し、紐付けしなかった理由を併せて説明することを推奨します。必須の入力フィールドは新たに追加しません。提出した ID はすべて有効で、本文が完全でなければなりません。そのうち一つでも失敗した場合は、今回の紐付け操作全体をロールバックします。報告と同時に明示的に紐付けを行い、それが失敗した場合は、報告全体をロールバックします。同じスナップショットを重ねて追加しても紐付けは増えず、説明も上書きされません。

## Agent ID の体系とレポートのバージョン

`report_finding` に任意のパラメータを新たに追加しました。配列の順序がそのまま初期の証跡の順序になります。

```json
{
  "traffic_refs": [
    {"traffic_id": "実際のトラフィック ID", "role": "baseline", "note": "正常アカウントのリクエスト"},
    {"traffic_id": "別の実際のトラフィック ID", "role": "proof", "note": "再現リクエスト"}
  ]
}
```

用途は `baseline`（正常時との比較）、`proof`（脆弱性の証明）、`verification`（補完検証）、`supporting`（補助的な証跡、既定値）です。まず `traffic_search` / `traffic_get` で実際のレコードを照合します。ドメインと時刻は候補を絞り込むためにのみ使い、作業への帰属を断定しません。

プロンプトは [CyberStrikeAI の脆弱性報告ツールの案内](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go) を参考にし、本プロジェクトの任意の紐付け規約と組み合わせていますが、紐付けしなかった理由を必須として検証するルールは設けていません。ID を推測してはならず、証跡を埋めるためだけに繰り返し検出を行ってもなりません。

戻り値の一行目は従来どおり `finding recorded: <探索ノード ID>` です。続く JSON は、独立した脆弱性レコードの `finding_id`、探索ノードの `finding_node_id`、紐付けの要約を提供します。

- `get_finding_traffic(finding_id)` は**独立した脆弱性レコードの ID** を使い、順序付きの一覧と `version` を返します。`binding_id`、`side=request|response`、`offset`、`length` を渡すと区間ごとに分けて読み取れます。一区間は最大 8192 バイトです。
- `update_finding_report` の `finding_id` は**引き続き探索ノード ID を使います。** 新たに追加した `evidence_version` には、実際に読み取ったバージョンを入れます。レポートを生成している間に証跡が変わった場合、古いバージョンの書き込みは拒否されるため、読み直して生成し直す必要があります。
- 古いレポート呼び出しがバージョンを渡さない場合、既存のトラフィック証跡を上書きしたとは見なしません。紐付け、説明、用途、並べ替えが変わると、既存のレポートに更新が必要であることを示す表示が付きます。

自動紐付けをオンにすると、`add_hint` / `add_task_hint` は、単一のヒントまたは一括の `hints` の各要素に `traffic_refs` を保存できるようになります。プランナーが代わりに報告する場合は `evidence_hint_id` を渡すことで、この作業に該当するヒント内の参照を明確に選択できます。継承されたヒントの参照は選択できません。システムは、ドメイン・時刻・照会履歴から紐付けを推測しません。提出が失敗した場合は、一部だけが作成された脆弱性を作ったり、レポートを前倒しでトリガーしたりはしません。

既存の脆弱性で紐付けが抜けている場合は、`bind_finding_traffic(finding_id, traffic_refs)` で補完的に紐付けでき、再登録する必要はありません。`list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail` は明確な `finding_id` と `finding_node_id` を返します。古い `id` は引き続き探索ノードの意味を保ちます。

起動時には、古いツールのスキーマに任意の属性だけを追加し、元の既定のトラフィックツールの紐付けをレポート Agent まで拡張します。補完用の紐付けツールは既定でレポート Agent に任せます。ユーザーが指定した紐付けリスト、プロンプト、説明、有効化の状態はそのまま維持します。案内は最終的なツールの組み立てが終わった後に、まとめて追加します。報告の役割は、すでに確保した証跡を引き渡す役割を担い、レポート Agent は照合・紐付け・レポート作成を担当します。プラットフォームの会話に作業の文脈がない場合は、構造化されたヒントを使って作業 Agent に引き渡す必要があり、直接報告はしません。作業の完了を判定する前に、まず既存の証跡を引き渡さなければなりません。ただし、紐付けるトラフィックがない場合に待機を強制することはしません。失敗した `report_finding` はレポート Agent をトリガーしません。

## API

基本パスは `/api/exploration/findings/{finding_id}/traffic` で、独立した脆弱性 ID を使います。認証は既存の方式にそのまま従い、`context_task` が作業の可視性と継承による読み取り専用かどうかを検証します。

メソッドおよび相対パスごとのリクエスト・戻り値は次のとおりです。

- `GET`: 順序付きの要約、証跡のバージョン、レポートが採用したバージョンを返します。
- `POST`: `{"traffic_refs":[...]}` を一度にまとめて追加します。
- `PATCH /{binding_id}`: `{"version":1,"role":"proof","note":"説明"}` で変更します。
- `DELETE /{binding_id}`: `{"version":1}` で削除します。
- `PUT /order`: `{"version":1,"binding_ids":["2","1"]}` で並べ替えます。完全な一覧でなければなりません。
- `GET /{binding_id}`: スナップショットのメタデータと、長さが制限された本文のプレビューを返します。
- `GET /{binding_id}/body`: `side`、`offset`、`length` を受け取り、`download=1` の場合は完全な元のバイト列をダウンロードさせます。

バージョン/並べ替えの集合の競合や、保管処理の進行中の書き込みは `409` を返します。継承された項目への書き込みは `403` を返し、存在しない、またはその脆弱性に属さない紐付けは `404` を返します。トラフィック/添付の読み取りと検証が失敗した場合は、明確にエラーを返します。

## 保存とマイグレーション

起動時に PostgreSQL に対して冪等なマイグレーションを実行します。`traffic_evidence_snapshots`、`finding_traffic_bindings` テーブルと、`findings.evidence_version` / `report_evidence_version`（既定値 0）カラムを新たに追加します。過去のテキストを根拠に、補完的な紐付けを推測することはしません。

スナップショットには、元のトラフィック ID、収集時刻、URL、メソッド、ステータス、リクエスト/レスポンスのヘッダー、本文の長さ、SHA-256 を保存します。本文はハッシュに応じて `<data>/evidence/blobs/<先頭 2 文字>/<hash>.bin` に保管されます。本文は整理対象の `data/traffic` とは分離されているため、複数の脆弱性がスナップショットや本文を共有できます。スナップショットには内容を更新するインターフェースはなく、検証が一致しない場合は読み取りとエクスポートが失敗します。

元のトラフィックの書き込みロックの下で、大きな本文の blob と古いディレクトリのレコードを含め、本文全体を読み取ります。まずファイルを永続化して検証し、その後一つの PostgreSQL トランザクションで、探索ノード、意図の関係、脆弱性、スナップショット、紐付けを記録します。コミットした後にようやくプランナーに通知します。失敗した場合、参照されないファイルが残ることはありますが、一部だけが記録された業務レコードは作られません。

PostgreSQL の advisory lock `7337741004` が、証跡ファイルと SQL の参照を調整します。作業の行ロックは、保管キューに入った後の証跡の変更を禁止します。復元は、本文のインストールからメタデータのコミットまでの全過程で証跡のロックを維持します。脆弱性を削除すると、紐付けも連鎖的に削除されます。

クリーナーは毎時間実行され、参照がなく、進行中でもない作業の内容だけを回収します。ただし最低 24 時間は遅延させます。通常のトラフィックの整理は証跡ディレクトリには触れません。ホットデータをバックアップする際は、PostgreSQL と `data/evidence` を一緒にバックアップします。

## エクスポートとアーカイブ

Markdown には順序付きの証跡一覧とバージョンが入り、JSON にはメタデータが、CSV には件数と紐付け ID が追加されます。`md-zip` は、脆弱性の Markdown を維持したうえで、次の構造も併せて提供します。

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown は相対リンクでパケットを参照します。ダウンロードを送る前に、添付のコピー、ハッシュの検証、圧縮、ディスクの同期、そしてすべての ZIP エントリの CRC の読み取り検証を完了させます。エントリが欠落している、または破損している場合は、ダウンロード全体が失敗します。完全な添付は、バイナリの元のバイト列をそのまま保持します。

アーカイブ v3 は、脆弱性の紐付け関係に従ってスナップショットと本文を収集し、元のトラフィックやドメインには依存しません。パッケージの検証を終えた後にのみホットデータを整理し、共有の証跡は引き続き保持します。復元では、先にインストールした本文を検証してから、トランザクションでメタデータと紐付けを復元します。失敗した場合は再試行をサポートします。v1/v2 も引き続き復元でき、欠落している新しいフィールドは明示的に 0 で埋めます。

## 検証と境界

テストパッケージごとに、独立して新たに作成した PostgreSQL のテストデータベースを用意し、`ARTEX_PG_DSN` で指定します。これにより、残っている作業/モデルのフィクスチャがバックグラウンド実行をトリガーすることを防ぎます。関連パッケージのテストを全件実行し、設定の欠落によりスキップされたテストがないことを確認します。

```sh
# 各パッケージを実行する前に ARTEX_PG_DSN を該当する独立したテストデータベースに設定します。明示的な設定が失敗した場合は、必ずエラーを返す必要があります。
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

フロントエンドの検証には、`npx tsc --noEmit`、影響を受けたファイルの Biome チェック、Webpack ビルド、`NEXT_EXPORT=1` の静的エクスポートが含まれます。独立したキャッシュディレクトリを使い、実行中の開発サーバーを上書きしないようにします。

ローカルのエンドツーエンドの受け入れ検証では、独立したポート、制御された HTTP / ドメイン HTTPS の対象、一時的なデータディレクトリを使用し、二つの紐付けの入口、複数ページにまたがる選択、並べ替え/説明、エラーの案内、継承による読み取り専用、ダウンロードを扱います。さらに、元のトラフィックを削除した後のエクスポート、アーカイブ、ホット本文の回収、復元とハッシュ検証までを含みます。

最初のバージョンでは、グローバルな証跡調整ロックを使用しています。大量の紐付け/エクスポートや、遅い添付のダウンロードが進行している間は、他の証跡の作業が待機することがあります。記録のレコードや完全な本文がなければ、証跡をでっち上げることはできません。この機能はキャプチャのスイッチを変更するものではなく、HTTPS で IP に直接アクセスする際の証明書の問題も扱いません。
