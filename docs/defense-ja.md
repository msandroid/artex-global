# 自律型 AI 攻撃の防御・検知ガイド

> 本書は、ARTEX のような**自律型 AI ペネトレーションエージェント**がどのように動作するかを防御側が理解し、その攻撃を**検知・遮断する能力**を養うための資料です。攻撃の手順を案内する文書ではありません。すべての内容は、自ら所有しているシステム、または書面による明示的な許可を得て検証するシステムを守る目的にのみ使用してください。許可なく他者の情報通信網を点検・攻撃する行為は、それ自体が犯罪です（[トップレベル README のセキュリティと悪用に関する警告](../README.ja.md)を参照）。
>
> 英語版: **[Defending Against and Detecting Autonomous AI Attacks (defense-en.md)](defense-en.md)**.

自律型 AI 攻撃ツールは、一人の人間が手作業で行っていたペネトレーションテストを、LLM エージェントが**自ら目標を分解し、実際のツールを実行して発見事項を蓄積する**24 時間の自動プロセスに変えます。防御者が向き合う相手は「熟練した攻撃者一人」から「疲れも休みもしないエージェントの群れ」へと変わります。本ガイドでは、その変化が検知と対応に何を求めるのかを整理します。

---

## 1. 自律型 AI 攻撃は既存のスキャナーと何が違うのか

従来の脆弱性スキャナー（例: 固定シグネチャに基づくツール）は、あらかじめ決められた点検項目を順番に投げかけて終わります。ARTEX のような自律エージェントは構造が異なります。[システムアーキテクチャ](../README.ja.md#システムアーキテクチャ)で説明したとおり、次の要素が組み合わさることで、**人の介入なしに複数段階の攻撃チェーンを最後まで完遂します**。

- **役割が分かれたマルチエージェント。** 目標を分解する `goals`、次の方向を判定して意図（intent）を出力する `planner`、意図を実際のツールで一つずつ実行する複数の `worker`、人が割り込む `mainagent` に分かれます。planner が唯一の意図生成者であり、worker がその意図を並列に実行します。
- **二重グラフに状態を蓄積。** 「何があるか」（資産グラフ）と「どこまでテストしたか」（探索グラフ）を別々に積み上げ、アンカーで結び付けます。そのため攻撃は**段階的に深まり**、同じ資産を別の角度から再訪し、先行する観察の上に次の段階を積み重ねていきます。
- **イベント駆動の閉ループ。** グラフが変化するたびに planner が起動して次の意図を割り当て、worker の書き込みがさらに次のラウンドを誘発します。目標が証明されるまで、この循環は止まりません。
- **直列の攻撃チェーンの安定した進行。** planner は「注入点の発見 → 認証情報の取得 → 横展開 → 権限昇格」のような依存順序を共有 todolist に一度記録し、先行段階が満たされた後続段階にだけ意図を割り当てます。そのため、ステートレスなセッション環境でも攻撃チェーンがずれることなく完遂されます。
- **LLM が文脈ごとにペイロードを変形。** 実行ツールとペイロードはコードに固定された定数ではなく、LLM が状況を読んで生成する値です。そのため、リクエストの形は一つひとつわずかに異なります。

### 検知がなぜ難しいのか

- **固定シグネチャが当てはまりにくい。** ペイロードは文脈ごとに変わるため、既知の悪性文字列を正確に一致させる方式のルール（WAF シグネチャ）はすり抜けやすくなります。
- **遅く、人のように区切って進めることができる。** エージェントはラウンドの間に休み、発見に応じて方向を変えます。そのため「短時間に多数のリクエストが来る」ことだけを見るレートベースの検知では見逃すことがあります。
- **偵察と侵入が一つの流れにつながる。** 人が偵察結果を見て数日後に手動で攻撃していた間隔がなくなり、最初の接触からデータ持ち出しまでの時間が大幅に短くなります。

### それでも検知できる理由: 振る舞いは隠しにくい

静的な指紋（User-Agent、特定のペイロード文字列）は、運用者がその気になれば変えられます。しかし**自律エージェントの振る舞いのパターン**は攻撃の本質に根ざしているため、変えることは困難です。以下の 2〜4 節は、この振る舞いベースの観点に重きを置きます。

- 一つの発信元が**性質の異なる複数段階のリクエスト**（偵察 → 列挙 → 認証試行 → エクスプロイト）を**一貫したセッションとしてつなげていく**パターン。
- 人間なら疲れて止まる時間帯にも**途切れることなく続く**探索。
- 失敗した応答からヒントを得て**次のリクエストを体系的に変形させていく**、無作為ではない適応的な進行。

## 2. 防御者が観測できる指紋（IoC・シグネチャ）

指紋は二つの観点に分けて見ます。**(a) 対象（被攻撃側）の観点**は、自社システムに向けられた ARTEX のトラフィックで確認できるものです。**(b) 運用者・フォレンジックの観点**は、ARTEX が実際に動作した（または侵害された中継の）ホストで確認できるものです。両者を混同しないことが重要です。対象側で見える静的な指紋は限られており、振る舞いの指紋が要になります。

### (a) 対象の観点: 自社システムに向かうトラフィック

- **エンリッチ（enrich）照会の User-Agent `artex-enrich/1.0`。** ARTEX は資産を自動でエンリッチ（DNS・HTTP による確認）する際、この User-Agent で対象に直接 `GET` を送ります（`enrich/enrich.go`）。この経路は LLM とは無関係に ARTEX 自身が生成するもので、**リダイレクトを追わず、keep-alive を無効にし、応答の先頭部分だけを読んで `<title>` を抜き出す**という特徴があります。デフォルトの同時実行数は 4 です。したがって、`artex-enrich/1.0` の UA による**短い接続・単発の GET・タイトルだけを読んで切断する**照会が複数の資産に同時に届いている場合は、ARTEX 系のエンリッチトラフィックを強く示唆します。ただし運用者は UA を変更できるため、**その不在が安全を意味するわけではありません。**
- **本攻撃のトラフィックはツールの既定の指紋に従います。** worker は実際のツール（Bash で実行する外部ツールや HTTP）でリクエストを送ります。ARTEX はこのトラフィックを自前の記録プロキシ経由にするため、サブプロセスの環境変数に `HTTP_PROXY` とプロキシ CA のパスを注入するだけで、**攻撃トラフィックに ARTEX 固有の User-Agent を強制することはありません。** そのため、対象側が見る User-Agent やヘッダーは、**その時点で実行されたツールの既定値**（各種コマンドラインツールの既定 UA）になります。運用者が変更していなければ一般的な自動化ツールの指紋が残り、変更していれば通常のブラウザを装っている可能性もあります。したがって、**単一の UA のマッチングに依存せず、振る舞いベースの検知と組み合わせる**必要があります。
- **worker 内蔵の WebFetch ツールは `norma/0.4` User-Agent を残します。** 上記の Bash 経由で実行される外部ツールと異なり、ARTEX が norma SDK（`github.com/Autumn-27/norma`）で直接行う HTTP 照会（WebFetch ツール）は、その SDK の既定の User-Agent `norma/0.4` を攻撃段階で送信します。平文 HTTP で通信する場合（または TLS 終端地点）ではネットワーク上で観測でき、[Suricata ルール sid 1000003](../detections/suricata/README.ko.md) がこの接頭辞（`norma/`）を検知します。ただし、この UA は ARTEX 固有のものではなく、norma SDK を使う他のツールも使うため、`artex-enrich/1.0` と同様に単独の証拠ではなく補助的な手がかりです。また、Bash で実行されたツールは各自の UA を使うため、**不在が安全を意味するわけではありません。**
- **内蔵のレートリミットがありません。** ARTEX 自体には対象トラフィック専用の速度制限がなく、リクエストの速度は LLM が動かす外部ツールが決めます。その代わり、タスクごとに worker が既定で 3 つ並列に動くため、一つの対象に**複数の意図が同時に**進行することがあります。つまり「ゆっくりした単一セッション」としても、「複数の角度からの同時進行」としても現れうるため、固定の閾値一つでは捉えにくくなっています。
- **振る舞いシグネチャ（最も重要）。** 以下のパターンの**同時出現**が自律エージェントを示唆します。
  - 一つの発信元（または少数の入れ替わる発信元）から、**偵察 → ディレクトリ・エンドポイントの列挙 → パラメータ探索 → 認証・注入の試行**が**短い間隔で連鎖**する。
  - 同じエンドポイントに対して、**応答コードや長さに反応して体系的に変形する**連続リクエスト（無作為のファジングではなく適応的）。
  - 人の運用時間帯を外れて**長時間途切れることなく**続くセッション。
  - 失敗（401/403/429）の後も止まらず、**迂回のための変形**を試みる執拗さ。

### (b) 運用者・フォレンジックの観点: ARTEX が動作したホスト

侵害調査で、中継・経由のホストに ARTEX がインストール・実行された痕跡を探す際に参照します。

- **既定の待ち受けポート `:8787`。** ARTEX サーバーの既定の HTTP 待ち受けアドレスです（`cmd/artex/main.go`、`--addr` で変更可能）。社内ネットワークのホストがこのポートで管理 UI（ダッシュボード・タスク・資産グラフ）を公開している場合、ARTEX インスタンスを疑う根拠になります。
- **記録型 MITM プロキシ `127.0.0.1:8788`。** worker の Bash・HTTP 実行を横取りして全過程を記録するローカルプロキシの既定アドレスです（`cmd/artex/main.go` の `--proxy` の既定値、ループバック専用）。自前の CA を生成して TLS を復号・記録するため（`mitmproxy-ca-cert.pem`）、ホストに **ARTEX がインストールした信頼 CA 証明書**があるか、サブプロセスに `HTTP_PROXY` やプロキシ CA のパスの環境変数を注入した痕跡があるかが手がかりになります。この注入は ARTEX が生成するすべての worker ツールに入り、変数名もソースにハードコードされている（`agent/worker.go`）ため、**実行中のプロセスがプロキシ変数と mitmproxy CA の信頼変数を併せ持っているか**は、ポート一つよりも特異的な指紋です。[ホスト分類ツール](../detections/triage/README.ko.md)が `/proc`（またはフォレンジックイメージではキャプチャした環境変数のダンプ）からこの組み合わせを確認します。
- **セルフアップデートのコールバック `artex-selfupdate`。** 自己アップデートが GitHub のリリースを照会する際に使う User-Agent です（`selfupdate/`）。送信（egress）ログで、この UA によるコードリポジトリホストへのリクエストが見えれば、ARTEX バイナリの存在を示唆します。
- **PostgreSQL 上の二重グラフ。** `exploration_nodes`・`assets`・`companies`・`activity` といったテーブルと、`agent_prompts` のシードがあるデータベースは、ARTEX のデータストアの特徴です。
- **DB に保存された正規表現の承認ルールと監査ログ。** ツール呼び出しを評価する intercept ルールが DB に保存され、優先順位どおりに正規表現で評価されます（`intercept/`）。遮断された呼び出しは監査ログ（`GET /api/audit`）に、`【ARTEX 平台管控·非目标防御】` で始まる管理上のフレーミングとともに記録されるため、侵害ホストの監査記録にこの文字列が見えれば、ARTEX の実行を裏付けます。
- **破壊的コマンドのハンティング指標。** ARTEX 自身のガードが遮断対象として内蔵しているコマンドパターンは、自律エージェントが**試みうる**コマンド群の裏返しです。ホストのコマンド監査では、次をハンティング指標としてください: `rm -rf`、`mkfs`、`dd of=/dev/`、`shred`/`wipe`、SQL の `DROP DATABASE`/`DROP TABLE`/`TRUNCATE`、MongoDB の `drop`/`dropDatabase`、Redis の `FLUSHALL`/`FLUSHDB`、`curl`/`wget` の `-X DELETE`、そして `curl … | nc …` のようなデータ持ち出しパイプです。ただし末尾のデータ持ち出しパイプは、データを破壊するコマンドではなく外部へ流出させる兆候であり、性質が異なります。前段の破壊パターンと違い、ARTEX のガードもこの規則だけは既定でオフのままにして内蔵しています（正当な点検用のリバースシェルやデータ転送パイプで誤検知が多いためです）。配布用の破壊コマンドのハンティングルール（[`destructive_command_hunting.yml`](../detections/sigma/destructive_command_hunting.yml)）も破壊の範囲に限定されており、この持ち出しパターンは含みません。そのため、持ち出しパイプは直ちに遮断せず、別のハンティング指標として扱い、環境に合わせて調整してください。

> 要約: **対象側の防御は振る舞いの指紋に掛け、静的な UA（`artex-enrich/1.0`・`norma/0.4` など）は補助的な手がかりとしてのみ使います。** 運用者・フォレンジックの指紋（`:8787`・`127.0.0.1:8788`・`artex-selfupdate`・DB スキーマ・監査ログのフレーミング）は、**侵害された経由ホストを調査する際に**有効です。

### IP アドレスの遮断がなぜ弱い一次防御なのか

セキュリティ事案が公になると、SNS やコミュニティには「攻撃 IP のリストを共有するので、ファイアウォールで遮断せよ」という投稿がよく出回ります。共有する側の善意とは別に、**出所の不明な非公式の IP リストをそのまま遮断ルールに入れることはお勧めしません。** 自律型 AI 攻撃では特にそうです。

- **出所を検証しにくい。** 個人が投稿した非公式のリストは、誰がどのような根拠で収集したのか確認する方法がなく、事案とは無関係な IP が混ざっていても除外する手段がありません。
- **すぐに陳腐化する。** 自律エージェントは VPN・クラウドインスタンス・乗っ取った中継サーバーを経由して、発信元 IP を頻繁に変えます（上記 (a) 節の「少数の入れ替わる発信元」）。昨日観測された攻撃 IP は今日には既に捨てられている可能性が高く、リストを遮断しても攻撃者は別の IP で戻ってきます。
- **誤遮断のリスクが大きい。** リストに共有ネットワーク帯域・CDN・正規のクラウド IP が混ざっていると、その IP を遮断した瞬間に正常な顧客トラフィックや内部サービスまで一緒に止まります。自動遮断（下記 6 節）と組み合わせると、誤遮断の被害はさらに速く広がります。

IP 遮断そのものが無意味というわけではありません。**公式の侵害指標（IoC）を対応機関や信頼できる脅威インテリジェンスから受け取り、有効期間と誤遮断の可能性を検討したうえで適用する**ことで、初めて意味を持ちます。ただし、IP を一つずつ遮断するのは回り続ける発信元を追いかける一時的な措置にすぎません。長く効くのは、変えにくい**振る舞い**（2〜4 節の振る舞いベースの検知）と、**攻撃対象領域の縮小**（3・5 節のハードニング: 公開資産の整理・パッチ・MFA）です。「指紋は変えられても振る舞いは隠しにくい」という本ガイドの前提が、ここでもそのまま当てはまります。

## 3. 攻撃者が狙う侵入点とハードニング

自律エージェントは、人間の攻撃者と**同じ弱点**を狙いますが、より速く、執拗に繰り返します。以下は防御の観点から見た優先的なハードニングのポイントです。

### 3.1 外部に公開された攻撃対象領域と既知（n-day）の脆弱性

自律エージェントが最初に、そして最も安定して狙う侵入点は、巧妙なゼロデイではなく、**外部に公開されたままパッチが当てられていない既知の脆弱性**です。境界機器（VPN・ファイアウォール）、外部に開いている管理・運用コンソール、アプリケーションサーバー・ミドルウェア・フレームワーク（例: 広く悪用される WebLogic・Struts 系）、そして**本サービスではなく、提携・採用・従業員用に付けられた補助システム**が代表的な標的です。自律エージェントは資産グラフで公開面を自動的に列挙したうえで、公開されたエクスプロイト（PoC）が出回っている n-day を、**パッチが適用される前に**数百の資産へ同時に狙います。脆弱な箇所を見つけて当てはめるこの過程の速さが、人間の攻撃者との差が大きく開く点です。

- **攻撃対象領域を減らす。** インターネットに公開している資産・管理コンソール・補助システムの一覧を継続的に維持し、外部に置く必要のないものは内部ネットワーク・VPN・許可リストの背後に移します。
- **既知の脆弱性を速やかにパッチする。** 境界機器・Web サーバー・アプリケーションサーバー・ミドルウェアで公開されている脆弱性（n-day）は自律エージェントの第一の標的となるため、公開 PoC が出回っているコンポーネントから、パッチ適用までの間隔をできる限り短くします。どれを先に対処するかは、実際の悪用が観測された脆弱性を集めた [CISA KEV（既知の悪用された脆弱性）カタログ](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)を優先順位の入力とし、7.1 節の国内の勧告（KISA 保護ナラ）と突き合わせてください。特定の CVE 番号を本文書に固定するのではなく、このように更新される公式の一覧を基準にするほうが、自律エージェントが新たに出回る n-day へ標的を移しても後れを取りにくくなります。
- **やむを得ず公開するインターフェースを絞る。** 外部に開けざるを得ない管理・運用インターフェースには、接続元の制限（IP 許可リスト）・MFA・VPN を加えて、認証なしの列挙そのものを防ぎます。
- **補助システムを本サービスと同じ基準で管理する。** 提携・採用・従業員用の補助システムも、本サービスと同じパッチ・監視の水準で管理します。自律エージェントが突く入口は、本サービスではなくこうした補助経路であることが少なくありません。認証フロー自体のハードニングは次の 3.2 につながります。

検知の観点では、特定の脆弱性の既知の経路（URL・パラメータ）を狙ったリクエストが外部から短い間隔で連鎖するなら、n-day スキャンの兆候です。この兆候は、2 節の振る舞いの指紋や、4 節の同一発信元による多段階の相関ルールと組み合わせたときに最もよく表れます。

### 3.2 補助的な認証・本人確認フロー

付加サービス・提携・採用チャネルのように**本サービスとは別の経路で付いている認証・本人確認フロー**は、検証が緩いことが多く、迂回の標的になります。自律エージェントはこうした経路を自動で列挙し、応答の差異を読み取って、迂回の条件を体系的に探します。

- 本人確認・認証の段階を**本サービスと同じ強度**に統一し、迂回可能な補助経路を網羅的に点検します。
- 認証状態の遷移（未ログイン → ログイン、一般 → 権限）を**サーバー側で再検証**し、クライアントが送ってきた信頼の印（Cookie・ヘッダー・パラメータ）をそのまま信じません。
- 本人確認トークンや一回限りのコードの**有効期間・再利用・推測可能性**を点検します。

### 3.3 API の認証・認可（IDOR・権限昇格）

- すべてのオブジェクトアクセスに対して**サーバー側での所有権・権限チェック**を強制します（識別子を変えるだけで他人のリソースが開いてしまう IDOR を遮断します）。
- 水平・垂直の権限昇格の経路を列挙して確かめます。自律エージェントは識別子を機械的に増減させながら大量に試行するため、**一件ずつの手動テストでは見逃す穴**をすぐに見つけ出します。

### 3.4 認証情報のスタッフィング（credential stuffing）

漏えいしたアカウント・パスワードの一覧を当てはめる攻撃は、自律エージェントが**速度と分散**によって増幅します。

- ログイン・本人確認のエンドポイントに**適応型のレートリミット**（IP・アカウント・デバイス・振る舞いに基づく）を設けます。
- 機微な操作には**多要素認証（MFA）**を強制します。スタッフィングでパスワードが一致しても、二段階目の認証で阻止できます。
- **認証情報の侵害検知**（既知の漏えいリストとの照合、異常なログインの場所・速度の確認）によって、先回りして遮断します。
- ログインの失敗・成功の**分布の変化**（急な低速・広範囲の試行）を警告します。

### 3.5 セッション・トークン・シークレットの管理

- セッショントークンの**範囲・有効期間・更新**を最小限にし、機微な遷移のたびに再認証します。
- API キーや内部トークンを、応答・ログ・エラーメッセージに**露出させません**（自律エージェントはエラー応答からヒントを積極的に収集します）。

## 4. 検知ルール・ログパターン（実務）

特定の製品に依存しない**疑似ルール**の形で記載します。ご自身の WAF・IPS・SIEM の文法に置き換えてご利用ください。以下のルールのうち、静的な指紋に基づくものは、すぐに配備できる [Sigma ルール（`detections/sigma/`）](../detections/README.ko.md)として提供しています。中核となる振る舞い・相関の検知（4.1・4.2）は単一のルールには還元できませんが、このうち ARTEX のコードで根拠を確認できた振る舞い指標は、配備可能な [Sigma 相関ルール（`detections/sigma/correlation/`）](../detections/README.ko.md)として提供しています（エンリッチ照会の速度・エンリッチ照会の対象数・ガード遮断のバースト・ガードマーカーと破壊コマンドの同一ホストでの同時発生）。ただし、その純粋な Web の多段階相関（列挙 → 探索 → 認証）のトラフィックは、単一の ARTEX 固有の UA には還元されないため、環境ごとのベースルールが必要です。この相関は下記 4.2 に、すぐに配備して試せる一般的な振る舞いベースの Sigma ベーステンプレートとして掲載しているので、ご自身の SIEM と基準値に合わせて調整し、出発点としてご利用ください。ネットワーク層で平文 HTTP で通信する場合（または TLS 終端地点）に観測される ARTEX の User-Agent は二つあり、どちらも [Suricata ルール（`detections/suricata/`）](../detections/suricata/README.ko.md)として提供しています。一つは enrich プローブの `artex-enrich/1.0`（存在シグネチャの sid 1000001・高速列挙の変種の sid 1000002）、もう一つは norma SDK の WebFetch ツールが攻撃段階で送る `norma/0.4`（sid 1000003）です。

### 4.1 WAF・IPS（振る舞いベース）

- 一つの発信元から、**性質の異なるリクエスト群**（静的リソースのリクエストの比率は低く、列挙・パラメータ探索・認証試行の比率が高い）が**一つのセッションとして**続く場合、スコアを上げます。
- 応答コードや本文の長さに**反応して変形する連続リクエスト**（エントロピーは高いがランダムではない適応パターン）を重み付けします。
- `artex-enrich/1.0` のような既知の自動化 UA は**直ちに高リスク**としてタグ付けしますが、UA が無いことを安全とは解釈しません。

### 4.2 SIEM 相関ルール

- **同一発信元の多段階相関**: 同じ IP/ASN/セッションから、(a) ディレクトリ・エンドポイントの列挙、(b) パラメータ探索、(c) 認証・注入の試行が**短い時間枠の中に全て**観測された場合、「自律攻撃の疑い」の警告を出します。
- **時間帯の異常**: サービスの通常のトラフィック分布から外れて、**長時間途切れることなく**続く単一セッション。
- **失敗後の持続**: 403/429 を受けても止まらず、**迂回の変形**を続ける発信元。

- 2 段階目（探索）は、インジェクション・トラバーサルのマーカー一覧に頼る粗いシグナルなので、単独では誤検知が多くなります。そのため三つの下位ルールの `level` は低く設定し、三つが同じ発信元で同時に現れる相関ルールでのみ高い警告になるようにしました。
- クライアントは `c-ip` でまとめています。プロキシや CDN の背後にいる場合は、`X-Forwarded-For` から復元した実際のクライアントアドレスやセッション識別子に置き換えてください。三つの段階をすべて要求することが厳しすぎて見逃しが出る場合は、三つのうち二つを満たしたときに発火するように緩和してください。

### 4.3 認証ログ

- アカウント・IP ごとの**ログイン失敗率の急変**、広範囲のアカウントにまたがる**低速の分散試行**（スタッフィングに特有）、失敗から成功への**異常な遷移速度**。
- 本人確認・一回限りのコードのエンドポイントに対する**列挙的なアクセス**。

### 4.4 送信（egress）・フォレンジック

- 内部ホストから、`artex-selfupdate` UA でコードリポジトリホストへ出ていくリクエスト。
- 内部で `:8787`（管理 UI）・`127.0.0.1:8788`（記録プロキシ）にバインドされているプロセス。
- `artex-enrich/1.0` の UA で、短時間に大量の外部資産を照会する DNS・HTTP のエンリッチパターン。

## 5. ハードニングのチェックリスト

防御組織がすぐに点検できるよう要約します。

- [ ] ログイン・本人確認・機微な API に**適応型のレートリミット**を適用している（IP・アカウント・デバイス・振る舞い）。
- [ ] 機微な操作に **MFA** を強制している。
- [ ] すべてのオブジェクトアクセスに**サーバー側の所有権・権限チェック**がある（IDOR の遮断）。
- [ ] 認証状態の遷移を**サーバー側で再検証**し、クライアントの信頼の印をそのまま信じない。
- [ ] **補助・提携・採用チャネル**の本人確認の強度を本サービスと統一している。
- [ ] 漏えいした認証情報の**侵害検知・照合**を運用している。
- [ ] WAF を**振る舞いベースのモード**で運用し、固定シグネチャだけに依存しない。
- [ ] **出回っている非公式の IP 遮断リストをそのまま適用せず**、公式の侵害指標（IoC）を信頼できる出所から受け取り、有効期間・誤遮断のリスクを検討したうえで反映している。
- [ ] SIEM に**同一発信元の多段階相関ルール**を入れている。
- [ ] 認証・アクセス・送信の**ログを十分な期間保存**している（自律攻撃は速いため、事後追跡の資料が重要）。
- [ ] インターネットに公開した資産・管理コンソール・補助システムの**一覧を維持して攻撃対象領域を縮小**し、境界機器・アプリケーションサーバー・ミドルウェアの**既知（n-day）の脆弱性を速やかにパッチ**している。
- [ ] ネットワークの**セグメンテーション**によって、横展開・権限昇格の被害範囲を狭めている。
- [ ] シークレット（キー・トークン）を**応答・ログ・エラーメッセージに露出させない**。
- [ ] **自動遮断・隔離**の対応を準備している（人の承認を待つだけでは自律攻撃の速度に追いつけない）。

## 6. インシデント対応の概要

自律型 AI 攻撃の特徴は**速度**です。一人の人間が一年かけて行う侵入・持ち出しを、エージェントははるかに短い時間で完遂できます。対応の設計もこの速度を前提にします。

- **自動遮断を先に。** 不審な発信元の隔離・セッションの無効化・レートの急低下のような措置を、人の承認前に**自動で発動**できるようにしておきます。すべてを人の承認ループに縛ると、攻撃の速度に追いつけません。
- **保存するログをあらかじめ決めておく。** 認証ログ、アクセスログ（リクエスト本文を含められる範囲で）、送信ログ、DNS クエリ。自律攻撃は痕跡を速く積み上げるため、事後に攻撃チェーンを復元するにはこれらの資料が必要です。
- **侵害範囲を資産単位で追跡する。** 攻撃は資産グラフに沿って広がるため、最初の侵入資産から横展開・権限昇格へ続いた**経路全体**を復元しなければ、再侵入を防げません。

### 6.1 疑わしいホスト・トラフィックの分類（トリアージ）手順

ARTEX の関与が疑われる場合に、最初に確認すべきことを順番に整理します。2 節で指紋を二つの観点に分けたように、分類も**(a) 自社のサービスが標的になったか**と**(b) 特定のホストで ARTEX が動作したか**に分けて見ます。どの段階でも、一つの一致だけで断定せず、複数の指標と振る舞いのシグナルが同時に現れるかで判断します。静的な指標がすべて見当たらなくても、振る舞いのシグナルが見えれば調査を続けます。

**(a) 対象側: 自社のサービスが ARTEX の標的になったか**

1. アクセス・認証ログで、エンリッチ照会の User-Agent `artex-enrich/1.0` を検索します。リダイレクトを追わない単発の `GET` 照会が、短い間隔で複数の資産に同時に届いていないか確認します（2 節 (a)）。運用者は User-Agent を変更できるため、ヒットしなくても次の段階に進みます。
2. 同一の発信元（または少数の入れ替わる発信元）から出ている**多段階の連鎖**を探します。偵察からエンドポイントの列挙、パラメータ探索、認証・注入の試行へと短い間隔で続き、応答コードや長さに適応し、401・403・429 の後も迂回の変形を止めない様子です。この振る舞いのシグナルは、静的な User-Agent よりも長く残ります（2 節 (a) の振る舞いシグネチャ）。
3. SIEM を運用している場合は、この振る舞いを [Sigma 相関ルール](../detections/README.ko.md)（エンリッチ照会の速度・対象数・ガード遮断のバースト・ガードマーカーと破壊コマンドの同時発生）で監視し、該当した発信元を上記の「自動遮断を先に」の原則に従って、隔離・セッション無効化の対象に上げます。

**(b) ホストのフォレンジック: 特定のホストで ARTEX が動作したか**

疑わしいホストで次を確認します。指標の根拠は、2 節 (b) と、機械可読な [侵害指標リスト](../detections/indicators/artex_indicators.csv) にあります。以下の五つの読み取り専用の点検のうち、最初の四つ（待ち受けポート・送信ログ・監査ログ・状態・記録ストレージ）は [ホスト分類スクリプト](../detections/triage/)（`detections/triage/artex_host_triage.py`）が一括で実行します。五つ目のコマンド監査は、破壊的コマンドが ARTEX 固有の指紋ではなく正当な管理者も使うハンティングの手がかりであるため、自動指標には含めず、スクリプトは代行せずにホストのコマンド履歴と直接突き合わせます。SIEM がなくシェルアクセスだけがある場合は、まずこれらを実行し、各ヒットは以下の説明のとおり手がかりとしてのみ扱ってください。

1. **待ち受けポート。** 既定のサーバーポート `:8787` とループバックの記録プロキシ `127.0.0.1:8788` が開いているかを、ホストで直接確認します。
   ```sh
   ss -ltnp | grep -E ':8787|:8788'   # ss がなければ netstat -ltnp を使います
   ```
   二つのポートは `--addr`・`--proxy` のフラグで変更されうるため、この照会が空でも、開いているポート全体と内部の管理 UI が起動していないかを併せて確認します。
2. **送信ログ。** 自己アップデートの User-Agent `artex-selfupdate` で、コードリポジトリホスト（GitHub リリース）へ出ていったリクエストが送信ログにあるか確認します（`selfupdate/`）。このホストで ARTEX バイナリが動作したことを示唆します。
3. **監査ログ。** ガードの管理マーカー `【ARTEX 平台管控·非目标防御】` が監査記録にあれば、ARTEX の実行を裏付けます（`guard/guard.go`）。遮断された各ツール呼び出しは、このフレーミングとともに記録されます。
4. **状態・記録ストレージ。** ARTEX は PostgreSQL に探索グラフを保持し（`exploration_nodes`・`assets`・`companies`・`activity` テーブルと `agent_prompts` のシード）、実行ファイルの隣にあるデータディレクトリ（`cmd/artex/main.go` の `--data` の既定値）に状態と記録を残します。このディレクトリ直下には、タスクごとの成果物を格納する `tasks/` と、会話記録を格納する `transcripts/` のサブディレクトリがあり、記録プロキシの成果物はその中の `traffic/` サブディレクトリに集められます（`server/manager.go` がデータディレクトリ直下の `traffic/` を記録プロキシのストレージとして開きます）。そのため、信頼する CA 証明書は `traffic/_ca/mitmproxy-ca-cert.pem`、トラフィックの索引は `traffic/_index/index.sqlite`、記録したリクエスト・レスポンスの本文は `traffic/_blobs/` にあります。これら三つが `tasks/`・`transcripts/` とともに見つかれば、記録プロキシが実際に動作していたことを強く示唆します。
5. **コマンド監査。** 破壊的コマンドのハンティング指標（2 節 (b) の末尾にある `rm -rf`・`DROP DATABASE`・`FLUSHALL`・持ち出しパイプなど）を、ホストのコマンド履歴と突き合わせます。正当な管理者も同じコマンドを使うため、手がかりとしてのみ扱います。

静的な指標（ポート・User-Agent・マーカー）は、運用者が変更・削除できます。したがって、**不在が安全を意味するわけではなく**、(a) の振る舞いのシグナルと (b) のホストの痕跡を併せて判断することが、自律型 AI 攻撃の分類の核心です。

## 7. 国内の公式チャネル: 侵害指標・セキュリティ勧告と届出義務

国内の防御組織は、侵害指標とセキュリティ勧告を公式のチャネルから受け取り、インシデントが発生した場合には法律で定められた届出義務を守る必要があります。出回っている非公式のリストの代わりに、以下の公式の情報源を一次的な基準としてください。

### 7.1 侵害指標・セキュリティ勧告の入手先

- **KISA（韓国インターネット振興院）の[保護ナラ（보호나라）・KrCERT/CC](https://www.boho.or.kr)** は、セキュリティ勧告・脆弱性の告知・侵害インシデント対応の情報を提供しています。サイバー脅威情報の分析・共有体制（C-TAS）によって、機関同士で脅威情報を共有しています（C-TAS は加盟機関の間で共有する仕組みであり、公開ポータルとは異なり別途の申請手続きを経ます）。
- **[金融セキュリティ院（FSI, 금융보안원）](https://www.fsec.or.kr)** は、金融分野の侵害・脅威情報を業界の枠を越えて共有しています（金融分野の ISAC）。金融業界にお勤めの場合は、このチャネルも併せてご確認ください。
- **[個人情報保護委員会（개인정보보호위원회）](https://www.pipc.go.kr)** は、個人情報漏えいの届出基準と保護措置に関する告示・ガイドを公開しています。

5 節のハードニングのチェックリストにある「公式の侵害指標を信頼できる出所から受け取る」が指しているのが、まさにこれらのチャネルです。公式の侵害指標であっても、有効期間と誤遮断のリスクを先に検討してから反映するという原則は、2 節の「IP アドレスの遮断がなぜ弱い一次防御なのか」で説明したものと同じです。

### 7.2 国内法上の届出義務

自律攻撃は速く広がるため、6 節のインシデント対応の手順の中に、法定の届出の段階をあらかじめ組み込んでおいてください。以下は要点であり、正確な適用対象・期限・要件は各機関の最新の告示で確認が必要です。

- **個人情報の漏えい**: 「個人情報保護法」（개인정보 보호법）第 34 条に基づき、漏えいを認識した時点から 72 時間以内に、個人情報保護委員会または KISA へ届け出るとともに、情報主体に通知します（情報主体 1,000 人以上、機微情報または固有識別情報の漏えい、外部からの不正アクセスによる漏えいなどが届出の要件に該当します）。
- **侵害インシデント**: 「情報通信網の利用促進及び情報保護等に関する法律」（정보통신망 이용촉진 및 정보보호 등에 관한 법률）に基づき、情報通信サービス提供者は、侵害インシデントを認識してから 24 時間以内に、科学技術情報通信部と KISA（KrCERT/CC）へ届け出ます。
- **金融機関**: 金融分野の監督規定により、金融監督院や金融セキュリティ院といった所管機関へ別途報告が必要な場合があるため、該当する規定も併せてご確認ください。

実際の届出は、侵害インシデントの場合は[保護ナラ](https://www.boho.or.kr)、または市外局番なしの 118（KISA サイバー民願センター）へ、個人情報の漏えいの場合は個人情報保護委員会の[個人情報ポータル](https://www.privacy.go.kr)で受け付けています。届出期限は短いため、担当者と連絡経路を 6 節のインシデント対応の手順にあらかじめ書き込んでおいてください。
