# ARTEX 侵害指標（機械可読）

日本語 · [English](README.md) · [한국어](README.ko.md)

ARTEX が自ら出力する固有の指紋を 1 つのファイルにまとめた、機械可読なリストです。検知ロジックではなく、原子的な指標そのものを求める防御者のためのものです。[`artex_indicators.csv`](artex_indicators.csv) を脅威インテリジェンス基盤や SIEM のルックアップテーブル、ホストのトリアージ（分類）チェックリストにそのまま取り込んでください。すべての値は、このリポジトリのソースで確認した文字列です。[検知ルール](../README.ko.md) と防御ガイド（[한국어](../../docs/defense-ko.md) · [English](../../docs/defense-en.md) の 2 節）が根拠としている、まさにその文字列です。各行には、その値の出所と（あれば）その上に構築したルールを記しています。

## 列の構成

- **`id`**: 指標の安定したスラグです。
- **`type`**: 指標の種類です: `http.user-agent`、`string`（ログやファイルで探すリテラル）、`port`、`ip-dst|port`、`other`（上記の分類に当てはまらないホストのアーティファクト。例: データベースのスキーマオブジェクト名）。これらは対応する MISP/STIX の属性タイプにマッピングされます。
- **`value`**: 正確な指標です。非 ASCII のガードマーカーを含め、原文のまま保存しています。
- **`perspective`**: `target`（ARTEX が探査しているシステムに向かうトラフィックで観測）か `forensic`（ARTEX が実行された、あるいは経由したホストの上で観測）です。防御ガイドはこの 2 つを意図的に区別しています。混同すると誤った結論に至ります。
- **`source`**: その値を出力する、リポジトリ基準の相対パスのソースファイルです（`;` で区切り）。これが根拠です。上流の再同期によって出力側が変われば、ここの指標も一緒に変わる必要があります。
- **`rule`**: その正確な値の上に構築された検知ルールです（`;` で区切り）。（騒がしい）ルールとして出力せず直接分類する、ホストのフォレンジック指標は空欄です。
- **`description`**: 一行の説明です。該当する場合は、正直な注意点を併記しています。

## MISP イベントのエクスポート

同じ指標を、そのまま取り込める [MISP](https://www.misp-project.org/) イベント [`artex_indicators.misp.json`](artex_indicators.misp.json) としても提供しています。MISP インスタンスを運用している（あるいは MISP 形式を取り込む脅威インテリジェンス基盤を使っている）防御者は、CSV の列を手作業でマッピングせずに指紋を直接取り込めます。STIX 2.1 は MISP 自身の変換機能で一度エクスポートすれば済むため、リポジトリが損失のある第二の形式を別に作ることはしません。

- **タイプのマッピング。** 各 CSV の `type` は、対応する MISP 属性タイプになります: `http.user-agent` → `user-agent`、ガードマーカーの `string` → `pattern-in-file`（カテゴリ *Artifacts dropped*）、`port` → `port`、`ip-dst|port` → `ip-dst|port`（合成値は MISP の `ip|port` 形式を使うため、`127.0.0.1:8788` は `127.0.0.1|8788` として保存されます）、探索グラフのスキーマ指紋 `other` → `other`（カテゴリ *Other*）。
- **`to_ids` は `rule` 列に正直に従います。** 検知ルールが立てられた行は対処可能な指標なので `to_ids: true` とします。ルールのないホストのフォレンジック行（既定の待受ポートとループバックのプロキシエンドポイント、および探索グラフのスキーマ指紋）は、ブロック用の IoC ではなく分類のヒントなので、`to_ids: false` に `disable_correlation: true` を付けています（一般的なポートや `127.0.0.1`、汎用のテーブル名が MISP の相関を汚してはならないためです）。これは CSV の `rule` 列と、下記の注意点がすでに含んでいる区別と同じです。
- **取り込み。** [pymisp](https://github.com/MISP/PyMISP) で `MISPEvent().load_file("artex_indicators.misp.json")` を使うか、*Add event → Populate from … → MISP format* の UI、もしくは REST API で取り込みます。イベントは未公開の状態で、`tlp:clear` タグが付いています。取り込み時に、インスタンスに合わせた配布範囲と公開状態を設定してください。

## このリストを正直に読むために

- **これらは変わりうる指紋であり、安全の証拠ではありません。** 運用者は User-Agent を別の値に設定したり、既定のポートを変更したりできるため、ここにある値がどれも*見つからない*からといって ARTEX が存在しないことを意味するわけでは**ありません**。長く有効なシグナルは振る舞いです。相関ルールと防御ガイドの 1・2・4.1〜4.2 節を参照してください。
- **一般的なハンティングの手がかりは意図的に除外しています。** 破壊的なシェル・DB コマンド（`rm -rf`、`DROP DATABASE`、…）は ARTEX の指紋*ではありません*。正当な管理者も実行します。取り込み用の指標ではなくハンティングの手がかりなので、このリストではなく [`destructive_command_hunting.yml`](../sigma/destructive_command_hunting.yml) と防御ガイドに置いています。これらをブロック用の指標として取り込むと、誤検知が生じます。
- **norma の WebFetch User-Agent はネットワークのシグネチャであり、取り込み用の原子的な指標ではありません。** ワーカーのページ取得ツールは攻撃段階で `norma/0.4` を送信し、Suricata ルール sid 1000003 は `norma/` の接頭辞に対して発火します。しかしこの文字列は norma SDK にハードコードされた独自の User-Agent（`github.com/Autumn-27/norma/tool/webfetch.go`）なので、norma の上に構築されたすべてのツールが同じように出力する値であり、ARTEX 固有の指紋ではありません。この値をブロック用の指標としてこのリストに入れると、すべての norma SDK のトラフィックで警報が鳴ります。これは破壊的コマンドを除外したのと同じ誤検知の罠です。そのため norma の UA はこのリストからは意図的に外し、ネットワークルールとしてのみ収録しています（[`../suricata/README.ko.md`](../suricata/README.ko.md)、sid 1000003）。また、この値はこのリポジトリのソースではなく、固定された依存関係（`github.com/Autumn-27/norma`）に根拠を置くため、下記の根拠テストは ARTEX 自身が出力する文字列を読み直すように、この値を読み直すことはできません。
- **ホストのフォレンジック用ポートはブロックではなく分類用です。** `:8787` と `127.0.0.1:8788` は、ARTEX を実行している可能性のあるホストを指します。`ss`・`netstat` で確認し、闇雲にファイアウォールで遮断しないでください。
- **探索グラフのスキーマ指紋はネットワーク・ファイルの IoC ではなく、DB 調査用です。** `exploration_nodes` テーブルは、ARTEX が PostgreSQL に置く探索グラフの中核テーブルです。単独のヒットで断定せず、兄弟テーブル（`exploration_edges`・`exploration_anchors`・`assets`・`companies`・`activity`）と `agent_prompts` のシードが同じデータベースに共存しているかで確認してください。運用者がテーブルを変更・削除できるため、存在しないことが安全を意味するわけではありません。
- **`rule` が空のホスト・DB 行には実行器があります。** Sigma ルールとしては出力せず直接分類する 3 つの指標、すなわち待受ポート・記録プロキシのエンドポイント・このスキーマ指紋は、[ホスト分類スクリプト](../triage/)が疑わしいホストで 1 つずつ点検します。そのため、シェルへのアクセスはあるが SIEM がない対応者も、`ss`・`netstat`・`psql` を手作業で実行する必要がありません。

## 検証

このリストは[指標の根拠（source-of-truth）テスト](../tests/indicators/run.sh)がカバーしています。この CSV を読み直し、すべての行について、その値が引用したソースファイルにまだ存在し、引用したルールに固定されていること、そしてテストが根拠とするすべての指標がリストに現れることを検証します。ソースとずれた行や、リストから抜け落ちた既知の指紋があると、テストは失敗します。次のコマンドで実行してください。

```sh
detections/tests/indicators/run.sh
```

MISP イベントは独自の [MISP エクスポート一貫性テスト](../tests/misp/run.sh)がカバーしています。イベントを pymisp で取り込み（すべての属性タイプがサーバーの受け入れる実在の MISP タイプになるように）、この CSV と行単位で同期していることを検証します。すなわち、同じ値、意図したタイプ・カテゴリ、そして `rule` 列に合わせた `to_ids` フラグです。イベントは CSV と並べて手作業で管理しています。CSV にはない、属性ごとに整理したコメント・安定した UUID・イベントレベルのタグも保持しているため、損失のある既定値でこれらを上書きする生成器はありません。CSV の行を追加・削除・タイプ変更するときは、同じコミットで [`artex_indicators.misp.json`](artex_indicators.misp.json) も合わせて修正してください（新しい属性には新しい `uuid` と、根拠となる `comment` を付けてください）。両者が一致するまでこのテストは失敗するため、更新を黙って忘れることはできません。次のコマンドで実行してください。

```sh
detections/tests/misp/run.sh
```
